### 2.4 数据质量问题（重读原始数据发现）

**① 节点 ID 不遵循类型前缀。** 设计上 `1x`=Root、`2x`=Recipe、`3x`=Ingredient、`4x`/`5x`=方法/工具、
`6x`=难度、`7x`=分类。但实际 **2905 个 Ingredient 和 2514 个 CookingStep 全部是 `20` 开头**，
与 Recipe 同号段——它们是按菜谱分块的私有子节点：

```
菜谱 201000001 咖喱炒蟹
  食材 201000002..201000010  (9 个)
  步骤 201000011..201000022  (12 个)
```

即食材和步骤的 ID 紧跟所属菜谱，**结构上就不存在跨菜谱共享的可能**。
这是「互不相交的星」的物理证据，比统计结果更根本。

> 影响：`nodeId >= '200000000'` 这类以号段判断类型的逻辑不可靠，只能靠 label。
> 导入脚本里 `WHERE row.nodeId >= '200000000'` 的过滤，恰好把元节点（`200000000/300000000`）
> 和真实实体混在同一区间，靠 label 区分而非 ID。

**② `relationshipId` 完全不能当唯一标识。** 它是**菜谱内序号**（`R_000001` 起、到 `R_000257` 止），
6055 条边只用了 **257 个不同 ID**，平均每 ID 复用 **23.6 次**，单条最多重复 **33 次**。
249 个 ID 存在重复。

> 影响：不能用 `relationshipId` 做主键、去重或引用依据。Day 11 的 `Evidence` 结构若要用
> `edge_ids`，必须用 `(startNodeId, endNodeId, type)` 三元组，或重建时生成全局唯一 ID。
> 上游 `neo4j_import.cypher` 直接把 `relationshipId` 写进关系属性，是个隐患——
> 若拿它做 MERGE 或索引，会把大量边误判为同一条。

**③ 食材名有语义等价但未合并的项。** 758 个名字中存在大量同义分裂：

| 名称 A | 数量 | 名称 B | 数量 |
| --- | ---: | --- | ---: |
| 大蒜 | 39 | 蒜 | 45 |
| 食用油 | 114 | 油 | 29 |
| 白糖 | 50 | 糖 | 27 |
| 姜 | 64 | 生姜 | 13 |
| 葱 | 50 | 小葱 | 23 |
| 酱油 | 36 | 生抽 | 108 |

> `synonyms` 字段（520 条非空）是 JSON 字符串，形如
> `[{'term':'鸡子','language':'zh',...}]`，但**不包含上述等价项**——
> 例如「蒜」的 synonyms 里没有「大蒜」。合并只能靠人工规则，不能只依赖 `synonyms`。
> 影响 Day 3：按 `name` 合并只能到 758，要真正对齐需要额外的同义词归一表。

**④ 器具被误抽成食材。** `刷子`（`201000066`）被建成 `Ingredient`，`category='工具'`，
并且有一条真实关系：`清蒸生蚝 --REQUIRES--> 刷子`（`amount=1, unit='把'`）。

根源是上游从**步骤文本**里抽食材时没有区分「食材」和「工具」。
`清蒸生蚝` 步骤 1 原文：

> 将生蚝用**刷子**刷干净（没有刷子用牙刷）。

该步骤的 `tools` 字段也记录为 `'刷子'`。也就是说，**同一个词同时被写进了食材和工具两处**。

用 `steps.tools` 字段交叉验证，共 **11 个名字**在食材表和工具字段中重叠：

| 名字 | 被多少道菜当食材 | 判定 |
| --- | ---: | --- |
| 水 / 油 / 开水 / 冰块 / 冷水 / 热水 | 53 / 29 / 17 / 10 / 6 / 4 | 语义双关，作食材可接受 |
| **刷子 / 保鲜膜 / 蘸料碟** | 各 1 | **确定是器具，应剔除** |
| 冰水 / 瓶装椰汁 | 各 1 | 可接受 |

> 影响：这 3 个名字会进入实体词表，可能被实体链接器匹配到用户问题里。
> Day 3 重建时应剔除，或迁移为 `CookingTool`。
> 更根本的问题：**工具只以字符串存在于 `steps.tools`，没有建成图实体**
> （`CookingTool` 节点全库只有 1 个元节点）。若要支持「哪道菜用蒸锅」这类问题，
> 需要把 269 个工具名实体化。

**⑤ 少量字段异常。** 1 道菜（半成品意面）步骤编号重复 `1..5` 两轮；
1 道菜的 `servings` 为空；9 条 REQUIRES 的 `amount` 为空但 `unit='适量'`；
152 条有 `amount` 无 `unit`；3 个食材名含数字（`100°C沸水`、`30°C温水`、`52%VOL白酒`）。

## 4. 关键基线：图是 322 个互不相交的星

| 指标 | 实测 | 含义 |
| --- | ---: | --- |
| 每个食材节点所属菜谱数 | **恒为 1**（2905 个） | 食材唯一归属一道菜 |
| 被 ≥2 道菜共享的食材节点 | **0** | **任意两食材连通 ⟺ 属于同一道菜** |
| 不同食材名 | **759**（含元节点）/ **758** 真实 | Day 3 合并目标 |
| 合并后跨 ≥2 道菜的名字 | **268** | 其中跨 ≥5 道菜 93 个 |
| 合并后最大跨菜数 | **141**（盐） | 最高频调料 |
| 合并后不同食材对 | **9147** | |
| 合并后多解食材对（≥2 道菜） | **1801** | 最大候选答案数 **62** |

**两个层面的证据**：

1. **统计层面**：2905 个食材节点的引用次数分布是 `{1: 2905}`——每个恰好被 1 道菜引用。
   任意两菜谱共享食材节点的对数 = **0**。
2. **结构层面**（更根本）：食材和步骤的 nodeId 紧跟在所属菜谱 ID 之后，
   是按菜谱分块的私有子节点（见 §2.4①）。**结构上就不存在共享的可能**。

**这意味着什么**：连通性判定在完美划分图上等价于「是否同菜」，
是查表而非推理。E1 的 AUC 会趋近 1.0，实验失去区分度。
按 `name` 合并后（2905 节点 → 758 真实食材），268 个食材跨多道菜，
同一食材对可对应多道菜（最多 62），多跳才成立。

> **Day 3 验收线：被 ≥2 道菜共享的食材从 `0` 变成 `268`，食材名从 `759` 降到 `758` 附近。**
> 达不到说明合并逻辑有问题。
>
> 注意：按 `name` 合并只解决「同名不同节点」，不解决「同义不同名」
> （大蒜/蒜、食用油/油 等，见 §2.4③）。要彻底对齐还需同义词归一表。

## 6. 面试问答

**Q1：`neo4j-init` 跑完就退出，你怎么知道导入了？静默失败怎么发现？**

A：容器退出码是第一个信号——`docker inspect --format='{{.State.ExitCode}}' neo4j-init`，
非 0 即失败，再看 `docker logs neo4j-init` 定位。`restart: "no"` 保证它只跑一次。

**但退出码 0 不等于数据对**：`cypher-shell -f` 遇到某些错误不会中断脚本。
所以要二次校验——用 `MATCH (n) RETURN labels(n)[0], count(*)` 取真实计数，
与 CSV 推算值逐项对比，并用总数兜底（防止某个 label 整体缺失却不被单列发现）。

> Day 1 就是靠总数行抓到一个解析问题：数据全对，但对比表全 0。
> 只看单列会误判成导入失败。

**Q2：5803 vs 5760，多出 43 个是什么？面试说哪个数？**

A：43 = **42 个脚本派生节点 + 1 个 Root 重复导入**。

- Category 19：按 `n.category` 逗号分割后 MERGE 出的分类节点
- ConceptType 8：按 `conceptType` 去重生成
- GraphStatistics 8 / RelationshipStatistics 7：脚本自己写的统计快照

**面试回答 5760**（CSV 原始），主动说明其余是导入脚本的派生结构。
说 5803 会让人误以为数据规模更大，一被追问就露馅。

进一步讲：派生节点会污染 `MATCH (n)` 全图遍历，`SIMILAR` 这类 `LIMIT 1000` 的
伪关系会混进证据集，Day 3 重建时应去掉——这体现的是「图模型要干净」。

**Q3：怎么发现「每个食材只属于 1 道菜」的？独立做项目第几天能想到？**

A：**先算基础统计、再看分布，而不是先写代码。**

路径：统计 CSV 时发现 `REQUIRES = 2905` 恰好等于 `食材数 2905`，
这个巧合可疑 → 查「每个食材被多少道菜引用」，得到分布 `{1: 2905}` → 确认是完美划分。

**关键判断**：连通性判定在完美划分图上等价于「是否同菜」，这是查表不是推理，
E1 的 AUC 必然趋近 1.0，实验没有区分度。

**诚实的回答**：独立做的话我大概率第 10 天跑 E1 时才发现（AUC 异常高），
然后倒推查数据。这次是提前查数据避开了。教训是：
**方法依赖某个数据特征时，应在写代码前先验证该特征存在**，而不是等实验结果异常再回头。

> 这也是为什么 Day 3 被标成分水岭：它是方法成立的前提，不是优化项。
