## 4. 关键基线：图是 322 个互不相交的星

| 指标 | 实测 | 含义 |
| --- | ---: | --- |
| 每个食材节点所属菜谱数 | **恒为 1**（2905 个） | 食材唯一归属一道菜 |
| 被 ≥2 道菜共享的食材节点 | **0** | **任意两食材连通 ⟺ 属于同一道菜** |
| 不同食材名 | **759**（含元节点）/ **758** 真实 | Day 3 合并目标 |
| 合并后跨 ≥2 道菜的名字 | **268** | 其中跨 ≥5 道菜 93 个 |
| 合并后最大跨菜数 | **141**（盐） | 最高频调料 |
| 合并后不同食材对 | **9147** | |
| 合并后多解食材对（≥2 道菜） | **1801** | 最大候选答案数 **62** |

**这意味着什么**：连通性判定在完美划分图上等价于「是否同菜」，
是查表而非推理。E1 的 AUC 会趋近 1.0，实验失去区分度。
按 `name` 合并后（2905 节点 → 758 真实食材），268 个食材跨多道菜，
同一食材对可对应多道菜（最多 62），多跳才成立。

> **Day 3 验收线：被 ≥2 道菜共享的食材从 `0` 变成 `268`，食材名从 `759` 降到 `758` 附近。**

## 6. 面试问答

**Q1：`neo4j-init` 跑完就退出，你怎么知道导入了？静默失败怎么发现？**

A：容器退出码是第一个信号——`docker inspect --format='{{.State.ExitCode}}' neo4j-init`，
非 0 即失败，再看 `docker logs neo4j-init` 定位。`restart: "no"` 保证它只跑一次。

**但退出码 0 不等于数据对**：`cypher-shell -f` 遇到某些错误不会中断脚本。
所以要二次校验——用 `MATCH (n) RETURN labels(n)[0], count(*)` 取真实计数，
与 CSV 推算值逐项对比，并用总数兜底（防止某个 label 整体缺失却不被单列发现）。

> Day 1 就是靠总数行抓到一个解析问题：数据全对，但对比表全 0。
> 只看单列会误判成导入失败。

**Q2：5803 vs 5760，多出 43 个是什么？面试说哪个数？**

A：43 = **42 个脚本派生节点 + 1 个 Root 重复导入**。

- Category 19：按 `n.category` 逗号分割后 MERGE 出的分类节点
- ConceptType 8：按 `conceptType` 去重生成
- GraphStatistics 8 / RelationshipStatistics 7：脚本自己写的统计快照

**面试回答 5760**（CSV 原始），主动说明其余是导入脚本的派生结构。
说 5803 会让人误以为数据规模更大，一被追问就露馅。

进一步讲：派生节点会污染 `MATCH (n)` 全图遍历，`SIMILAR` 这类 `LIMIT 1000` 的
伪关系会混进证据集，Day 3 重建时应去掉——这体现的是「图模型要干净」。

**Q3：怎么发现「每个食材只属于 1 道菜」的？独立做项目第几天能想到？**

A：**先算基础统计、再看分布，而不是先写代码。**

路径：统计 CSV 时发现 `REQUIRES = 2905` 恰好等于 `食材数 2905`，
这个巧合可疑 → 查「每个食材被多少道菜引用」，得到分布 `{1: 2905}` → 确认是完美划分。

**关键判断**：连通性判定在完美划分图上等价于「是否同菜」，这是查表不是推理，
E1 的 AUC 必然趋近 1.0，实验没有区分度。

**诚实的回答**：独立做的话我大概率第 10 天跑 E1 时才发现（AUC 异常高），
然后倒推查数据。这次是提前查数据避开了。教训是：
**方法依赖某个数据特征时，应在写代码前先验证该特征存在**，而不是等实验结果异常再回头。

> 这也是为什么 Day 3 被标成分水岭：它是方法成立的前提，不是优化项。
