## 2. 原始图为什么判不了连通

Day 1 已经发现「每个食材只属于 1 道菜」，Day 3 把它量化到可验收：

| 事实 | 数值 |
| --- | ---: |
| `REQUIRES` 边 | 2905 |
| 食材节点 | 2905 |
| `recipes_per_ingredient` 分布 | `{1: 2905}` |
| 被 ≥2 道菜共享的食材 | **0** |
| 15048 个食材对，每个对应的菜谱数 | 全部 = 1 |
| 图结构 | 322 个互不相交的星 |

**根因**：食材是按「菜谱 × 食材」逐条抽出来的，同一食材在不同菜里是不同节点。
`大蒜` 39 个节点、`蒜` 45 个，共 84 个，每个只挂 1 道菜；`生抽` 108 个、`酱油` 36 个，共 144 个。
同一道菜的食材之间没有任何边相连，跨菜的同名节点更是毫无关系。

## 3. 重建前后，同一个查询实际返回什么

这一节是重建的全部意义所在。下面四条查询在两张图上执行，结果完全不同。

### 3.1 「大蒜能做什么菜」

```cypher
MATCH (i:Ingredient {name:'大蒜'})<-[:REQUIRES]-(r:Recipe)
RETURN r.name
```

| | 原图 | 新图 |
| --- | ---: | ---: |
| 返回行数 | **39** | **84** |
| 说明 | 另有 45 个节点叫「蒜」，用「大蒜」查不到 | 两个名字已归一，一次查全 |

### 3.2 「哪两道菜共享食材」

```cypher
MATCH (a:Recipe)-[:REQUIRES]->(i:Ingredient)<-[:REQUIRES]-(b:Recipe)
WHERE a <> b
RETURN a.name, i.name, b.name
```

| | 原图 | 新图 |
| --- | ---: | ---: |
| 有向结果 | **0 行** | **59407 行** |
| 无向对数 | 0 | 29703 |
| 覆盖菜谱 | 0 / 322 | 316 / 321 |

原图返回 0 行不是查询写错了，是图上确实不存在长度为 2 的 `Recipe→Ingredient→Recipe` 路径。

### 3.3 「从咖喱炒蟹出发，能走到哪些菜」

```cypher
MATCH (a:Recipe {nodeId:'201000001'})-[:REQUIRES]->(i:Ingredient)<-[:REQUIRES]-(b:Recipe)
WHERE a <> b
RETURN DISTINCT b.name
```

| 口径 | 原图 | 新图 |
| --- | ---: | ---: |
| 全部食材 | **0** | **222** |
| 只用主料（`isMain=true`） | 0 | **0** |

新图里的具体路径举例：

```
咖喱炒蟹 -[大蒜]→   水煮鱼
咖喱炒蟹 -[大蒜]→   清蒸生蚝
咖喱炒蟹 -[食用油]→ 红烧鱼
咖喱炒蟹 -[食用油]→ 红烧鱼头
咖喱炒蟹 -[食用油]→ 小龙虾
```

### 3.4 为什么「只用主料」还是 0

咖喱炒蟹有 9 个食材，按被多少道菜使用排序：

| 食材 | 主料? | 用量 | 被多少道菜使用 |
| --- | :---: | ---: | ---: |
| 食用油 | | 30 ml | 143 |
| 大蒜 | | 5 瓣 | 84 |
| 鸡蛋 | | 1 个 | 72 |
| 淀粉 | | 5 g | 39 |
| 洋葱 | | 200 g | 24 |
| 开水 | | 300 ml | 17 |
| 咖喱块 | | 15 g | 3 |
| **青蟹** | **✓** | 300 g | **1** |
| 椰浆 | | 100 ml | 1 |

它唯一的主料「青蟹」只出现在这一道菜里，所以按主料算，咖喱炒蟹与整张图没有任何连接。
那 222 道菜全部是经由食用油、大蒜、鸡蛋这些辅料连上的。

## 4. 重建动作清单

计划里归纳为七件事，这里拆成十项，逐项对应前后数字。

| # | 动作 | 前 → 后 |
| --- | --- | --- |
| 1 | 删 schema 占位节点 `200000000`(菜谱) / `300000000`(食材) | 节点 −2 |
| 2 | 按 `name` 合并同名食材 | 2905 → 758 |
| 3 | 按同义词归一（9 组） | 758 → 746 |
| 4 | 剔除器具误抽：刷子 / 保鲜膜 / 蘸料碟 | 节点 −3 |
| 5 | 合并重复菜谱「陈皮排骨汤」 | 菜谱 322 → 321 |
| 6 | 补齐缺失的 4 类 RecipeCategory | 分类 9 → 13 |
| 7 | 由 `category` 重生成 `BELONGS_TO` | 边 314 → 327 |
| 8 | 删因去重而失去父节点的 CookingStep | 步骤 2514 → 2507 |
| 9 | `relationshipId` 重编号 | 唯一值 257 → 6047 |
| 10 | `isMain` 从 Ingredient 节点搬到 `REQUIRES` 边 | 650 条主料边保留 |

第 10 件容易漏：食材节点被合并后，`isMain`（主料/辅料）这个属性无处可放。
它原本在 Ingredient 节点上（652 个 `True` / 2253 个 `False`），必须跟着搬到 `REQUIRES` 边上，
否则「只用主料」这类消融根本做不了——而正是这个字段揭示了下面第 6 节的问题。

### 4.1 同义词只做已核实的 9 组

`synonyms` 字段里存的是 `淡色酱油`、`鲜味酱油` 这类别名，**不包含**「大蒜/蒜」这种真同义词。
手工核对了计划里列的 10 组，确认 9 组在两个名字都真实存在于数据中，才做归一：

| 归并 | 保留 | 归并 | 保留 |
| --- | --- | --- | --- |
| 蒜 | 大蒜 | 酱油 | 生抽 |
| 油 | 食用油 | 黄酒 | 料酒 |
| 糖 | 白糖 | 生粉 | 淀粉 |
| 生姜 | 姜 | 干辣椒 | 辣椒 |
| 小葱 | 葱 | | |

效果：`生抽` 143 道菜、`食用油` 143、`大蒜` 84、`料酒` 74。

归并后有 3 处「同一道菜里两个别名撞车」，按规则合并用量：
萝卜炖羊排×料酒 `30-40 ml`、辣椒炒肉×生抽 `3+2 = 5 ml`、姜葱捞鸡×鸡腿 `4个+400克`（单位不同，成对保留不换算）。

### 4.2 重复菜谱保留哪一条

两条「陈皮排骨汤」的 7 个步骤文本完全相同，食材名也相同，但：

| | 201003873（保留） | 201004002（删除） |
| --- | --- | --- |
| 难度 | 4.0 | 3.0 |
| 准备时间 | 5 分钟 | 10 分钟 |
| 食材用量 | 有克数 | **全空** |
| tags | 广东老火靓汤、熬夜党必备、注意防烫 | 同左 + 养生 |

保留有克数的那条，把对方独有的 `养生` tag 并进来。

### 4.3 `category` 拆成两个字段

原数据里 Recipe 和 Ingredient 共用 `category`，枚举却完全不兼容（13 种菜系 vs 7 种食材类）。
导入脚本用 `MATCH (n) WHERE n.category IS NOT NULL` 建 `Category` 节点，结果 19 个分类节点里
混着「荤菜」和「调料」——跨 label 的语义污染。重建后拆成 `recipeCategory` / `ingredientCategory`。

## 6. 连通性是谁撑起来的

「0 → 255」这个对比很容易让人以为连通性问题解决了。看每道菜的 1 跳可达菜谱数：

| 口径 | 平均 | 中位 | 最大 | 完全孤立 |
| --- | ---: | ---: | ---: | ---: |
| 全部食材（2892 条边） | **178.0** | 213 | 273 | **5** / 321 |
| 只用主料（650 条边，22.5%） | **12.5** | 2 | 69 | **90** / 321 |

全部食材口径的可达数分布：

| 可达菜谱数 | 0 | 1–50 | 51–150 | 151–250 | 251+ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 菜谱数 | 5 | 37 | 40 | 217 | 22 |

结论很清楚：**连通性主要由调料撑起来**。使用度前 10 的食材是
食用油 143、生抽 143、盐 141、大蒜 84、姜 77、白糖 77、料酒 74、葱 73、鸡蛋 72、老抽 57——
全部是调料或常备辅料。只保留主料（650 条边，占 22.5%）后，321 道菜里有 90 道（28%）一个邻居都没有。

全部食材口径下仍然孤立的 5 道菜：

| 菜谱 | 食材数 | 原因 |
| --- | ---: | --- |
| 完美水煮蛋 | 4 | 4 个食材都只出现在这一道菜 |
| 空气炸锅面包片 | 1 | 只有 1 个食材 |
| 冰粉 | 4 | 4 个食材都只出现在这一道菜 |
| 砂糖椰子冰沙 | 3 | 3 个食材都只出现在这一道菜 |
| 炸薯条 | 1 | 只有 1 个食材 |

这意味着两件事：

1. 「两菜共享食材」这条路径的**语义强度很低**。咖喱炒蟹和水煮鱼之所以相连，唯一原因是都用大蒜；
   这不构成「这两道菜相似」的证据。
2. Day 4 的实体链接和 Day 7 的 benchmark 必须**按 `isMain` 分组**，否则测出来的是「调料命中率」，
   而不是「食材理解能力」。这也是我保留第 10 项动作的原因。

## 7. 导入脚本重写了什么

`data/rebuild/neo4j_import.cypher` 与原脚本 `data/C9/cypher/neo4j_import.cypher` 的差别：

| | 原脚本 | 新脚本 |
| --- | --- | --- |
| 节点类型 | 13 类（含 4 类派生） | 8 类 |
| 关系类型 | 11 类（含 5 类伪关系） | 4 类 |
| `Category` / `ConceptType` | 建 | 不建 |
| `GraphStatistics` / `RelationshipStatistics` | 建（各 8 / 7 个） | 不建 |
| `SIMILAR` / `USES_SAME_TOOL` / `USES_SAME_METHOD` / `NEXT_STEP` | 用 `LIMIT 1000` 截断生成 14193 条 | 不建 |
| 空值 | 写成空字符串 | 写 null |
| APOC 依赖 | 需要 | 不需要 |
| 重跑 | 会残留上一轮关系 | 开头 `DETACH DELETE` 清空 |

伪关系为什么必须去掉：它们不是数据里的事实，是按「同分类/同工具」推导出来的，
且被 `LIMIT 1000` 截断。留着会让连通性判定看起来有效，实际是虚假捷径。

### 7.1 为什么用独立实例

新 compose 用容器名 `neo4j-rebuild`、端口 7475/7688、独立数据卷，
`data/C9/` 的原始环境完全不动，两套图可以同时跑、随时对比。

代码连新图只需在 `.env` 里加一行：

```
NEO4J_URI=bolt://localhost:7688
```

## 8. 新发现的数据缺陷

### 8.1 `relationshipId` 根本不能当主键

6055 条边只有 **257 个**唯一 `relationshipId`。`R_000001` 在 2905 条 `REQUIRES` 里被用了 248 次——
这是个按批次重置的计数器，不是主键。

原导入脚本用 `MERGE (source)-[r:REQUIRES]->(target)` 按端点匹配，所以没出事；
但任何「按 relationshipId 查边」的代码都会拿到一堆无关结果。重建时按输出顺序重编为 `R_000001…R_006047`。

### 8.2 10 道菜没有 `BELONGS_TO` 边

314 条边只覆盖了 312 道菜。缺失的 10 道恰好就是 `半成品` 这个分类——
分类枚举里有 13 个取值，`RecipeCategory` 节点却只有 9 个，`半成品` / `凉菜` / `下酒菜` / `减肥餐` 根本没有节点。

另外 4 道菜的 `category` 是多值（如 `皮蛋瘦肉粥` = 汤类,早餐,主食），但只连了 1 个分类节点。
重建后按 `category` 全量重生成，327 条边、321 道菜全覆盖、多分类完整保留。

### 8.3 器具被当成食材

`刷子`(201000066)、`蘸料碟`(201000833)、`保鲜膜`(201000869) 三个节点 label 是 Ingredient，
`category` 是「工具」或「其他」。已删除。

数据里 `CookingTool` 只有一个占位节点 `500000000 烹饪工具`，没有真实工具实例体系，
所以没法「改标成工具」——单为这 3 条边新建一套 `USES_TOOL` 关系不划算。
它们混在 Ingredient 里的真正危害是污染 Day 4 的实体链接：问句里出现「刷子」会被当成食材匹配。

### 8.4 删除重复菜谱会留下孤儿步骤

`201004002` 的 7 个 CookingStep（201004010–201004016）只被它引用，
删菜谱后这 7 个步骤就成了无边节点，一并删除。

## 10. 面试问答

**Q1：你说图不能判连通，怎么证明不是检索代码的问题？**

不用跑代码，查数据就能证。`REQUIRES` 边数 2905 恰好等于食材节点数 2905，
说明每个食材节点只被引用一次；`recipes_per_ingredient` 的分布是 `{1: 2905}`，没有第二个值。
图论上这就是 322 个互不相交的星，任意两菜之间不存在经过食材的路径。
重建前后我跑过同一条 Cypher：查「两菜共享食材」原图返回 0 行，新图返回 59407 行。
检索代码再怎么改，也不可能查到不存在的路径。

**Q2：合并食材节点，怎么保证没有把不同东西合到一起？**

只做两类合并，都有数据依据。第一类是 `name` 完全相同——这没有歧义。
第二类是同义词，我没有凭常识直接合，而是先核对两个名字是否都真实存在于数据中，
计划里列的 10 组里确认了 9 组。像「酱油/生抽」这种其实有层级关系的（生抽是酱油的一种），
我按数据里出现的用法合并，并在报告里记录了每一组的合并明细，可回溯。

**Q3：为什么要删掉 SIMILAR 这类关系？它们不是能增加连通性吗？**

能增加，但增加的是假的。这些关系是按「同分类」「同工具」推导出来的，
不是数据里的事实，而且被 `LIMIT 1000` 截断——只保留了任意 1000 条。
留着它们，连通性判定会得到虚高的数字：任意两道菜都可能因为「都用炒锅」而连通。
那样测出来的不是一个图算法有效，而是我给自己造了一条捷径。

**Q4：255 个共享食材，占 34.2%，这个比例够用吗？**

够支撑连通性判定，但我在第 6 节主动把它的局限量化了：连通性主要由调料撑起来。
全部食材口径下平均每道菜能到 178 道菜，中位数 213；只算主料就掉到平均 12.5、中位 2，
321 道菜里有 90 道完全孤立。咖喱炒蟹连到水煮鱼，唯一原因是都用大蒜——这不是「相似」的证据。
所以我不会说「连通性问题解决了」，我会说「图上有了路径，但路径的语义强度分层很明显」。
这个分层直接决定了 Day 4 的实体链接要按 `isMain` 分组，Day 7 的 benchmark 要按实体分组，
否则测出来的是调料命中率，不是食材理解能力。

**Q5：为什么保留 `data/C9/` 不动，另建一套？**

原始数据是 Day 1 普查的基准，也是复现的起点。如果直接覆盖，
之后所有「重建前后对比」的数字都无法复核，出了问题也无法回退。
代价是多一份 852KB 的 CSV 和一个独立容器，这个代价很小。

**Q6：`relationshipId` 重复这件事，上游为什么没发现？**

因为导入脚本没把它当主键用——`MERGE` 是按端点匹配的，`relationshipId` 只是 `SET` 上去的属性。
只要没人按它查，重复就不会暴露。这类缺陷的共性是：不影响主流程，但会让「按 id 追溯」这类需求静默失效。
我是做引用完整性检查时顺手统计了唯一值才发现的。

**Q7：食材合并后，`isMain` 这种节点属性你放哪了？**

搬到 `REQUIRES` 边上。食材节点是「一道菜用了某食材」这个事实的两端，
`isMain`、`amount`、`unit` 描述的都是这条边而不是食材本身——主料/辅料是相对某道菜而言的，
同一样食材在 A 菜是主料、在 B 菜可能是辅料。放在节点上本身就是建模错误，
原数据把它放在 Ingredient 上只是因为节点是按「菜谱 × 食材」逐条抽出来的，一节点对一菜谱，才碰巧成立。
