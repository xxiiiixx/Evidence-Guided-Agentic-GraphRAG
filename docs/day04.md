# Day 4 执行记录：给大模型一份图谱名单，让它只做选择

日期：2026-10-23

## 0 一句话结论

`dual_level_retrieval` 里那次耗时 14.8 s 的 LLM 调用，问题不在「用了大模型」，而在提示词让模型**凭空猜实体名**。改成把整份图谱名单（**1 117 条**）放进提示词、规则改成「只能逐字复制名单里的字符串，名单里没有就返回空」，模型就从「生成」变成「选择」，产出天然能换回真实节点：一次选择得到一个 `nodeId`，下游按 id 取数，不再有「名字对了但节点不存在」的落空。

代价是一次模型调用（延迟回到秒级），换来的是**输出可对齐、可评测、编不出图外的东西**。

## 1 为什么改

### 1.1 Day 2 的分段计时

`perf/timing` 分支上实测一条问句（`docs/day02.md` §8.3）：

| 阶段 | 耗时 | 占检索 |
| --- | --- | --- |
| `dual_level_retrieval` | 14 808.8 ms | **88.4%** |
| 其中 `extract_query_keywords()`（一次 LLM 调用） | 14 799 ms | 88.3% |
| 向量检索 | 1 949.5 ms | 11.6% |
| BM25 | 2.0 ms | 0.01% |
| RRF 融合 | 0.1 ms | <0.01% |
| **检索合计** | **16 760.4 ms** | 100% |

### 1.2 根因：提示词在让模型编名字

旧提示词（`hybrid_retrieval.py` `extract_query_keywords`）写着：

> 1. 实体级关键词：具体的食材、菜品名称、工具、品牌等有形实体
>    - 例如：鸡胸肉、西兰花、红烧肉、平底锅、老干妈
>    - **对于抽象查询，推测相关的具体食材/菜品**

最后那句是本末倒置：它明确要求模型去**推测**图谱里可能并不存在的名字。模型照做了，而下游 `graph_indexing.get_entities_by_key()` 是**按名字精确查字典**：

- 猜的名字不在图上 → 整条落空，14.8 秒白花，而且不报错；
- 猜的名字撞上别的节点 → 召回错误内容。

图谱里一共只有 1 117 个候选。这不是需要推理的任务，是查表任务——模型该做的是**在这张表里指**，不是**照着例子造**。

### 1.3 Day 2 召回混进 Ingredient 的直接原因

Day 2 三次运行的召回里每次都有 1–2 条是 Ingredient（`201000002` 青蟹、`201000004` 洋葱），而 chunk 只挂在 Recipe 上（Day 3 已确认 `build_recipe_documents()` 只 `MATCH (r:Recipe)`）。原因是两层叠加：

1. `entity_kv_store` 以 nodeId 为键，但 `get_entities_by_key(name)` 按名字建的索引**不区分类型**；
2. 模型猜出来的「青蟹」「洋葱」正好是食材名 → 直接命中食材节点，作为一条检索结果进了 top-5。

现在模型选中一条候选就带回它的 `nodeId`（以及 label），检索按 id 直取，**同名不同类不会再串**。

## 2 走过的弯路：确定性匹配

第一版把 LLM 整个去掉，改成纯 Python 的 Aho-Corasick 在 1 280 个表面形式上做最左最长匹配。它跑得极快（单条 0.008 ms），26 条标注问句 26/26。**然后被否掉了**，理由有两条：

**① 26/26 是自己出题自己答。** 标注集里的问句都包含图上真实存在的名字，而确定性匹配的原理就是「问句里出现名字就命中」——这种评测只能证明实现没写错，不能证明方案好。

**② 它的上限是词表覆盖率，而覆盖率很薄。** 746 个食材里只有 17 个（2.3%）带 `synonyms`，加上 Day 3 归一出来的 9 组，总共只覆盖 146 条别名。等价表达一律失效：`松花蛋→皮蛋`、`土豆→马铃薯`（图上另有「马铃薯」节点）、「咖哩」（喱）、任何错别字。更致命的是**没有实体名的意图类问句**：`今天想吃点清淡的`、`有没有快手的菜`、`家里来客人做什么`——词表匹配只能返回空，而这类问句在真实使用里占相当比例。

结论：把判断力整个删掉不是简化，是把「可改善的差」换成「不可改善的空」。判断该由模型做，工程要做的是**把它的输出关进笼子**。

## 3 现在的做法

### 3.1 名单从哪来

`rag_modules/graph_vocabulary.py` 只做一件事：把图上真实存在的名字整理成提示词要的字符串，**不做任何匹配**。

| 指标 | 值 | 说明 |
| --- | --- | --- |
| `recipes` | 321 | 菜谱节点 |
| `ingredients` | 746 | 同义词归一之后 |
| `recipeEntries` | 321 | 菜名（含 `mergedAliases` 归一进来的原名） |
| `ingredientEntries` | 746 | 食材名 |
| `topicEntries` | 50 | 13 个菜谱分类 + 31 个菜系 + 5 档难度 + 归并 |
| `entries` | **1 117** | 名单总条数 |
| `aliasRefsRaw` | 1 346 | 原始别名引用（`synonyms` + `mergedAliases`） |
| `aliasRefs` | **146** | 过滤后留下的别名 |

别名砍掉 89%，因为这份数据里有大量机器生成的怪别名（`tomato土豆炖牛肉`、`sweet and sour汁`）。规则：**含 ASCII 字母或数字的丢掉、超过 12 字的丢掉、每条最多留 3 个**。塞进提示词既费 token 又会诱导模型照抄——`西红柿土豆炖牛肉` 一条菜谱原本带 7 个别名，其中 5 个是这种货色。

主题（分类 / 菜系 / 难度）也从菜谱属性派生：`topic_level_retrieval` 本来就是按这三样查的，模型得先能点名它们。

### 3.2 提示词结构

`rag_modules/llm_entity_extractor.py`：构造时把名单编译成**静态前缀**（6 607 字符），之后每条 query 只拼问题本身——问题放在最后，是为了让上游的 prefix cache 能命中。

规则原文（要点）：

1. 只能返回名单里的名字，逐字复制。不得改写、补全、翻译、简写、合并或纠正错别字。
2. 名单写成「规范名（别名1、别名2）」。问题里出现别名时，选它对应的规范名，并**只输出括号前的规范名**。
3. 名单里没有对应的名字时返回空数组；不得用近义词、俗称、相似说法或自己编的名字代替。
4. 只挑问题里**明确提到**的名字；不得推测「可能相关」的食材、菜品或分类。
5. 每份名单最多 8 个，按相关性从高到低排列。
6. 只输出一个 JSON 对象：`{"recipes": [], "ingredients": [], "topics": []}`

`temperature=0`（抽样只会削弱「逐字复制」这个约束），`max_tokens=256`。

### 3.3 笼子写在代码里，不靠模型自觉

模型仍可能不守规矩，所以校验是硬编码的：

- **名单外的名字直接丢弃**，记进 `dropped` 并打 warning，绝不拿它去模糊匹配——那等于把「模型编的名字」重新放回检索路径；
- 模型照抄别名（返回「生姜」而不是「姜」）会被 `entry_for()` 换回规范名，**这是允许的**，因为别名本来就在名单里；
- 键名不对（比如退回旧提示词的 `entity_keywords`）、JSON 解析失败 → 重试 1 次，仍失败则返回空结果并打 error，检索退回向量 + BM25，**不抛异常**；
- `max_per_type` 截断，防止模型把整份名单抄回来。

### 3.4 三条可切换的臂

`config.keyword_source`：

| 取值 | 行为 | 用途 |
| --- | --- | --- |
| `llm_vocab`（默认） | 闭集抽取 | 线上路径 |
| `llm_open` | 旧提示词，自由猜名 | 对照实验（Day 7） |
| `none` | 不抽关键词，只用向量 + BM25 | 消融基线 |

`main.py --trace` 现在会把 `keywords` 字段写进 jsonl：`keyword_source`、`matched_entities`（含 `surface`/`name`/`label`/`node_id`）、`matched_topics`、`dropped_surfaces`、`prompt_chars`、`attempts`、`link_elapsed_ms`。「模型到底选了哪些名字」从此可查。

## 4 顺带修掉的 7 处（都不报错，只是静默失效）

### 4.1 五处指向旧 schema

`OPTIONAL MATCH` 匹配不到只给 null，`elif` 分支进不去只是少挂几个键——所以只能靠读代码发现。

| 位置 | 旧写法 | 重建图里实际是 |
| --- | --- | --- |
| `graph_data_preparation.py:100` | `(r)-[:BELONGS_TO_CATEGORY]->(c:Category)` | `(r)-[:BELONGS_TO]->(c:RecipeCategory)` |
| `graph_data_preparation.py:107,110` | `COALESCE(r.category, ...)` | `r.recipeCategory` |
| `graph_indexing.py:239` | `relation_type == "HAS_STEP"` | `CONTAINS_STEP` |
| `graph_indexing.py:247` | `relation_type == "BELONGS_TO_CATEGORY"` | `BELONGS_TO` |
| `hybrid_retrieval.py:435,444` | `r.category CONTAINS ...` / `r.category as category` | `r.recipeCategory` |

第一处后果最严重：分类全部变成「未知」，而因为写在 `OPTIONAL MATCH` 里，日志上一切正常。

### 4.2 两处逻辑

**按名字去重会把实体删掉。** `graph_indexing.deduplicate_entities_and_relations()` 原来按 `entity_name` 分组，把同名实体的内容并进第一个、并**从 `entity_kv_store` 删除**其余的。11 组菜谱/食材同名（牛排、小龙虾、凉皮…）里食材那一半会被合并掉，之后按 nodeId 取就是空。改成按 `(entity_name, entity_type)` 去重后两者共存。

**同义词归一必须读 `mergedAliases`。** Day 3 把「生姜」并进「姜」，原名只写进 `mergedAliases`（纯文本），而 `synonyms` 是 JSON 数组。只读 `synonyms`，「生姜」就查不到「姜」——Day 3 那 9 组归一在检索侧等于没做。这个洞是标注集报出来的：`大蒜和生姜` 只命中了大蒜。

| 单元测试 | **36 条全通过** | `python -m unittest discover -s tests` |
| 管线契约 | **26/26** | `python scripts/eval_keyword_source.py`（contract 模式） |
| 掺假名拦截 | 26 条问句、**78 个**图外名字全部进 `dropped`，`leaked = []` | 同上 |
| 名单规模 | 1 117 条 / 6 607 字符静态前缀 | `results/keyword_source_eval.json` |
| 管线自身开销 | **0.009–0.044 ms**（均值 0.018 ms，不含模型） | 同上 |
| 真实模型准确率 | **未测** | 本机没有 API Key |

标注集 26 条：20 条含实体（裸菜名、菜名+问法、同义归一、跨 label 同名、分类/菜系/难度主题词），6 条是意图类问句（期望返回空）。

### 5.1 contract 模式量的是什么，不是什么

它**不衡量模型质量**。做法是把标注里的期望名字当成「一个完美模型的回答」喂给管线，要求 100% 还原成正确 `nodeId`；再故意掺进图上没有的名字（`红烧肉`、`五花肉`、`松花蛋`——图上只有红烧冬瓜/红烧猪蹄/红烧茄子），要求它们全部被丢弃且不影响结果。

它证明的是一条代码保证的硬约束：**模型编出来的名字进不了检索路径**。这条约束不依赖模型表现，所以可以离线验证。

它**不能**证明第 6 条规则「不得推测」被遵守——那只能看真实模型。所以今天关于「闭集提示词准不准」这个问题**没有答案**，只有待办：`python scripts/eval_keyword_source.py --source llm_vocab`（需要 `MODELSCOPE_API_KEY`）。

评测脚本里还有一道防呆：标注里写了名单里没有的名字会直接 `exit 2` 并列出是哪条——避免标注写错被当成模型不行（写第一版时就撞了一次：`番茄炒蛋` 不在图上，图上叫 `西红柿牛腩`）。

## 6 代价与取舍

### 6.1 每条 query 一次模型调用，延迟回到秒级

这是主动选择，不是回退。Day 2 的 14.8 s 之所以是问题，是因为它花 14.8 秒换来「一堆可能不存在的名字」；现在花同样量级的时间换来「一组确定的节点」。要压延迟有两条路，都留到后面：名单前缀走 context cache；或用 `--no-build` 常驻进程摊销。

想完全不要这次调用，`keyword_source=none` 就是纯向量 + BM25 基线——消融时正好做对照。

### 6.2 名单外的说法，模型也没辙

规则禁止它用「名单里没有但意思接近」的名字。所以 `松花蛋`、`咖哩`、错别字仍然失效——除非这些写法进了别名表。当前 146 条别名覆盖了 17 个食材的 `synonyms` + 9 组 `mergedAliases`，这就是今天的能力边界。

这是刻意的：放宽成「可以返回近义写法」就等于放弃可对齐性，又回到 §1.2 的问题。

### 6.3 单字名现在能进名单了

弯路版本按设计丢掉单字表面形式（冰 姜 水 盐 米 肉 葱 虾 醋 面 鸡），因为子串匹配会在「水煮鱼」里命中「水」。闭集方案里判断者是模型：它看得见「盐」也看得见「水煮鱼」，会选后者。所以 `盐放多少` 现在能命中 `盐`——这是相对弯路版本的实质进步，不是取舍。

### 6.4 `max_per_type = 8` 是拍出来的

没有数据支撑「8」这个数。超过 8 个名字的问句在 26 条标注里没出现。等 Day 7 的真实 query 集上来再调，现在只是防止模型把整份名单抄回来的护栏。

## 8 面试问答

**Q1：把整份名单塞进提示词，是不是太粗暴了？**
粗暴但正确，而且规模允许。1 117 条、6.6k 字符的静态前缀，比很多 system prompt 都短。业界常规做法是先召回候选再让模型选（两阶段），但这里的候选池本身就小，一次给全反而更简单：没有召回率这个中间变量，也没有「候选召回错了模型再好也没用」的故障面。等词表上到十万级，就必须改成先检索候选——那时才需要引入向量召回候选层。

**Q2：那和把答案写在提示词里有什么区别？**
区别在「模型做什么」。写答案是把输入输出都固定死，模型没有作用；这里是模型在 1 117 个选项里做选择，而且必须处理「一句话里同时提到菜、食材、分类」这种组合，输出顺序和数量都由它判断。「梨」这个候选是数据给的，但「问咖喱炒蟹该选哪几个」是模型判断的。

**Q3：怎么防止模型不守规矩？**
不指望它自觉。名单外的输出被 `dropped` 并丢弃，键名不对就重试，重试失败就返回空结果让检索退回向量 + BM25。规则是软的，校验是硬的——这也是为什么 contract 模式能离线证明「编的名字进不来」，而不用等真实模型。

**Q4：为什么不干脆去掉大模型（确定性匹配）？**
试过，26/26，然后否决了。原因写在 §2：那个准确率是自己出题自己答，而且方案上限是 146 条别名能覆盖的写法。真实问句里「清淡一点」「来客人做什么」这类没有实体名的意图，它只能返回空；把判断力删掉不是简化，是把可改善的差换成不可改善的空。

**Q5：既然还是调大模型，Day 2 那个 14.8 s 的问题解决了吗？**
解决了「花了 14.8 秒却拿不到可用结果」这个真问题，没解决「慢」。区别在于：以前的 14.8 秒产出一堆查不到的名字，等于全浪费；现在的调用产出一组带 nodeId 的确定节点，时间花在了有用的地方。要压总延迟，得靠 context cache 或常驻进程摊销，那是工程问题不是方案问题。

**Q6：`temperature=0` 就能保证确定性吗？**
不能完全。同一个模型、同一段提示词，输出仍可能因为批次/并行实现而微变，模型换代更会变。真正的保证是 §3.3 那层校验：不管它返回什么，能进检索路径的只有名单里的名字。对 benchmark 复现来说，这个保证比「输出逐字相同」更实用。

**Q7：为什么要在 `dropped` 上打 warning 而不是静默丢弃？**
因为 `dropped` 是**唯一能观测「模型想编什么」的信号**。如果某个词反复出现在 `dropped` 里（比如很多人问「松花蛋」），那就说明词表该补这条别名——这是数据迭代的输入，静默丢弃就把这个信号扔了。

**Q8：这份名单和 Day 3 的图重建是什么关系？**
名单从重建图派生：746 个食材是 Day 3 同义归一之后的数量，别名里的「生姜」来自 `mergedAliases` 列。所以 Day 3 做的归一，在 Day 4 才真正对检索生效——这也说明「数据改了」和「数据生效了」是两件事，中间隔着代码有没有读到。
