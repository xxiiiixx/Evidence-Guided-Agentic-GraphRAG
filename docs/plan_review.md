## 2. 计划的结构性问题

### 2.1 【严重】算法 novelty 不足，这是天花板问题

计划的唯一主线是 `Evidence-Guided Budget-Aware Adaptive Retrieval`：

```
Query → 初次检索 → 证据评估 → {充分: 停 | 不足: 补检索 | 预算耗尽: 拒答}
```

**这条线是 Self-RAG / CRAG / Adaptive-RAG 的直接组合。** 你在计划 §5 自己列了这三篇文献（`28_day_plan.md:227-228`），说明你知道它们存在，但没意识到你已经把自己框进了它们的射程。

面试官看到这个设计会问三个问题，而**以目前的计划，你三个都答不好**：

| 面试官的追问 | 你目前的答案 | 致命性 |
| --- | --- | --- |
| "你和不加反馈、直接 Always-Combined 有什么区别？" | 能省一点工具调用 | 如果消融显示 Always-Combined 准确率更高，你的工作就变成了"用准确率换成本"，**这是个负结果** |
| "Self-RAG 已经有反思 token 和检索门控，CRAG 已经有证据质量分级，你的增量是什么？" | "我用了实体覆盖和关系覆盖" | 这是**特征工程层面的替换**，不是方法层面的贡献 |
| "你的评分器 `C = w_e·C_entity + w_r·C_relation + w_q·C_relevance`，权重怎么来的？" | "开发集调试" | 三个权重在 40 条数据上调，**必然过拟合**，而且无法证明泛化 |

**更麻烦的是：这个设计的收益上界很低。** 你的 Baseline 是 C9 教学代码，它的问题不是"路由不够聪明"，而是"图检索根本没实现"。等你把 `_find_entity_relations` 补上，**收益主要来自 Bug 修复，而不是来自控制器**。这正是你自己在 `baseline_analysis.md:130` 担心的事，但计划没有给出应对方案——只说了"要分开记录"，没说"分开之后如果控制器没收益怎么办"。

### 2.2 【严重】Day 1–3 的时间分配和风险顺序反了

计划把 Neo4j / Milvus / 模型 API 的验证放在 Day 2–3，也就是**在投入 10 小时写文档之后**。这是典型的"先做舒服的事"。

正确的顺序是：**Day 1 上午先把环境跑通，下午再读代码**。理由：

- 环境跑不通的概率不低于 40%（Milvus 需要独立部署，`torch==2.6.0` 是硬钉版本，BGE 模型要下 100MB+，Kimi API 要 key）
- 环境失败会**推翻整个计划的技术前提**，越早发现越能调整
- "我跑通了端到端" 这个事实本身，就能让后续所有文档的可信度上一个台阶

现在你的 Day 1 是"读代码 + 写笔记"，如果 Day 3 环境炸了，前 10 小时的工作会有一半作废。

### 2.3 【中】Benchmark 的 Gold 会系统性偏向 Graph

计划 `28_day_plan.md:118` 自己写了：

> **不得**将 Gold 答案/路径作为 Agent 运行时输入。合成模板问题可能偏向 Graph，需要按问题类型分桶并加入自然改写。

**意识到了，但没有给出解法。** "分桶"和"自然改写"都不是解决方案：

- 分桶只能让你**事后看到**偏差，不能消除偏差
- 自然改写如果由 LLM 做，会引入 LLM 的分布偏好；如果人工做，40 条还能撑，200 条会拖垮进度

真正的解法是**引入一个不依赖图的金标准**：从菜谱原文（Neo4j 里的 `description` / CookingStep 文本）生成问题，答案的验证不查图、只查文本。这样 Graph 和 Hybrid 站在同一起跑线上。这个改动必须写进 Day 5–6。

### 2.4 【中】指标定义有坑

`Evidence Recall@5` 和 `Path Recall@5` 这两个指标，**只在你自己的 Gold 路径定义下才成立**。但问题是：

- 同一道菜可能有**多条**合法支撑路径（A→REQUIRES→鸡肉，或 A→CONTAINS_STEP→步骤→提到鸡肉）
- 如果你的 Gold 只存了其中一条，Agent 走了另一条合法路径会被判错
- 这会让你的方法**被系统性低估**，而且消融结果不可信

必须在 Day 6 之前定义清楚：**"路径等价"的判定规则**是什么。建议存 Gold 时存"最小充分证据集"（一组必须被覆盖的 node_id-shorthand 三元组），而不是存一条具体路径。

### 2.5 【低但要注意】28 天 / 112 小时的现实性

112 小时 ÷ 28 天 = 每天 4 小时，**连续 28 天无休**。这对有课/有实习的人是极高强度。计划的降级机制（§6 三档交付）写得不错，但降级触发点太晚（Day 17 / Day 21）。

建议改成**每周日做一次 Go/No-Go 判定**，而不是等到 Day 21 才发现做不完。

### 3.2 【严重】图路径检索的空实现不是"待修复"，是"整条链路断的"

计划把 `_find_entity_relations` / `_find_shortest_paths` 描述为"部分为空实现"（`baseline_analysis.md:90`）。**实际比这个严重。**

看 `graph_rag_search` 的分派逻辑（`graph_rag_retrieval.py:500-517`）：

| `query_type` | 走哪条路 | 实际结果 |
| --- | --- | --- |
| `MULTI_HOP` | `multi_hop_traversal` → 可变长路径 Cypher | 能出结果（但有路径爆炸风险） |
| `PATH_FINDING` | `multi_hop_traversal` → **`_find_shortest_paths` → `return []`** | **恒空** |
| `ENTITY_RELATION` | `multi_hop_traversal` → **`_find_entity_relations` → `return []`** | **恒空** |
| `SUBGRAPH` / `CLUSTERING` | `extract_knowledge_subgraph` | 能出结果 |

`ENTITY_RELATION` 正是**最高频的查询类型**（"哪道菜含鸡肉和土豆"就是它）。也就是说：

**你的 Graph 基线在最常见的问题类型上，召回率恒为 0。**

这不是"部分为空"，这是**基线本身在主要场景下不可用**。直接后果：

- 你的 B2（仅 Graph）基线**没有意义**，它测的是一个恒返回空的系统

- 因此 **Ours vs B3 的对比才是唯一有效的对比**，B0 只能作为"缺陷记录"存在

这个结论必须写进 Day 1 文档，它直接决定了你 Week 2 的工作量和 Week 3 的实验设计。

→ **修正：`_find_entity_relations` 的优先级从 Day 8 提到 Day 4–5，且必须在 Day 7 的 Baseline 冻结之前完成，否则 B3 对照无意义。**

## 4. 如何达到大厂算法岗标准（这是你真正要回答的问题）

### 4.1 先明确：大厂面试官怎么看你这个项目

我把 DeepSeek / 腾讯 / 字节的算法岗面试逻辑拆给你：

**第一层（前 5 分钟）：这项目是不是真的？**
- 有没有真实运行记录？→ 你目前 0 条
- 指标是不是编的？→ 你的状态标注很诚实，这点加分
- 数据是自己造的吗？→ 是合成的，会被追问

**第二层（5–20 分钟）：技术深度**
- 为什么这么设计？替代方案是什么？
- 边界条件、失败案例、参数敏感性
- 遇到什么问题，怎么解决的

**第三层（20–40 分钟）：研究品味**
- 这个工作的 **insight** 是什么？（不是 "我加了个控制器"，而是 "我发现 X 现象，所以设计了 Y"）
- 和已有工作的本质区别
- 如果给你更多资源，你会怎么做

**你目前的计划能过第一层（如果补上运行记录），会在第二层被卡住，第三层几乎没有准备。**

### 4.2 必须补的三个"深度锚点"

面试里你需要的不是"我做了一个 Agent"，而是**三个能讲 10 分钟的具体技术点**。我建议从现有代码里挖这三个：

#### 锚点 A：RRF 的"同源重复加分"陷阱 —— 你已经踩到了

`hybrid_retrieval.py:630-700` 的 `_rrf_merge` 有一段很精细的实现：

```python
# 同 source 内同 doc_id 多次命中（如一道菜的多个 chunk 共享 recipe.nodeId）：
#   - 算分只取该 source 内最佳 rank（最小 rank）一次，避免重复加分
#   - 命中 chunk 数另存到 rrf_chunk_hits，供后续分析
```

**这是整个仓库里最有含金量的代码**，而且计划完全没提。

为什么重要：一道菜被切成 5 个 chunk，如果 5 个 chunk 都命中，naive RRF 会给这道菜的 5 个 chunk **各加 5 次分**，导致一道菜霸占全部 top-k。这段代码用 `node_id` 做了归并，只取最佳 rank。

**你的机会**：这正好是你 Controller 的 `Evidence Novelty` 特征（计划 `28_day_plan.md:53`）的**现成基础设施**——`rrf_chunk_hits` 已经记录了"同一文档被多少个 chunk 命中"，这本身就是个 novel 信号。

→ 把这个写进 `baseline_analysis.md`，并在面试里作为"我读懂了别人的精妙设计"的例证。

#### 锚点 B：证据充分性为什么不能只看关键词覆盖 —— 你的反例

你已经在 `baseline_analysis.md:99-105` 构造了这个反例。**但它现在只是一个例子，还不是一个方法。**

把它升级成方法：定义一个 **Evidence Sufficiency** 的形式化：

```
充分 ⇔ 存在一个证据集合 S，使得：
   (a) 覆盖查询的全部必需实体 E_q
   (b) 对每对需关联的实体 (e_i, e_j)，S 中存在一条连通路径
   (c) S 的规模 ≤ 预算上限
```

条件 (b) 是关键——它把"关键词覆盖"升级为"**连通性覆盖**"。这个定义可以直接用 Neo4j 的 `MATCH p = shortestPath(...)` 验证，是**可计算的、确定的、不依赖 LLM 的**。

**这就是你的 insight**：不是"我加了个反馈循环"，而是"**我把证据充分性从文本相似度问题，转化成了图上的连通性判定问题**"。后者是可验证的，前者不是。

这句话能撑起整场面试。

#### 锚点 C：预算约束下的最优停止 —— 这是真正的算法问题

计划里"预算 2 次检索"是拍脑袋的。**它可以变成一个真问题**：

给定
- 每轮检索的成本 `c_i`（Hybrid 和 Graph 成本不同）
- 当前证据的边际增益 `Δ(e)`（新增多少 entity / path 覆盖）
- 剩余预算 `B`

决策：继续 / 停止。

这本质是**带预算的序列决策 / optimal stopping**。你不需要真的解出最优解，但你**必须能说清楚**：

- 为什么用贪心（每步选边际增益最大的工具）是合理的近似
- 贪心的失效条件是什么（比如两个工具单独都无效，但组合有效）
- 你的实验能不能验证这个失效条件

**能讲清楚这段，你从"调参工程师"变成"算法工程师"。**

### 4.3 修正后的项目定位

现在的定位：**"给 GraphRAG 加反馈控制器"**（工程改进，novelty 低）

建议的定位：

> **"证据充分性的可验证判定与预算约束下的检索策略"**
>
> 核心观察：现有 RAG 用文本相似度判断"检索够了没"，但相似度不能证明"多条证据共同支持一个多跳结论"。
> 本文把充分性定义为图上的连通性覆盖问题，给出可计算的判定算法，并在预算约束下求解检索策略。
> 在 200 条基于真实图谱的 Benchmark 上，相比 Always-Combined 降低 X% 工具调用，同时保持/提升准确率。

差别在于：**前者是"我做了什么"，后者是"我发现什么问题，所以提出什么方法"。** 面试官只对后者感兴趣。

## 6. 给你的三条硬规矩

1. **没跑过的东西，不许写进文档的"已完成"部分。** 你现在的状态标注习惯很好，继续保持，但要把"检查完成"这种模糊表述换成"执行了 X 命令，输出在 Y 文件"。

2. **每天结束前，仓库里必须多一个可验证的产物。** 可以是一个 JSON、一张截图、一段日志，但不能只有一段文字。文字是最容易自欺欺人的东西。

3. **每周日回答一个问题：如果今天面试，我能讲 20 分钟吗？** 如果不能，说明这周的工作没有沉淀成可讲述的东西，下周调整。
